Bayangkan server mengirim:
```
{
  "id": 17,
  "name": "Dede",
  "email": null
}
```

Kita ingin mengubah JSON tersebut menjadi Swift model.

Model yang benar:
```
struct User: Codable {
    let id: Int
    let name: String
    let email: String?
}
```

Kenapa?

Karena backend mengatakan:
```
id
→ ada angka

name
→ ada String

email
→ null
```

Maka Swift model harus sesuai:
```
Int
String
String?
```

Sekarang perhatikan kalau programmer menulis:
```
struct User: Codable {
    let id: Int
    let name: String
    let email: String
}
```

Tetapi server mengirim:
```
"email": null
```

decoding dapat gagal.
Ini sangat penting.

Masalahnya bukan:
```
internet putus
```

Melainkan:
```
JSON berhasil diterima
↓
struktur data server
tidak cocok
dengan model Swift
↓
decode gagal
```

Ini menjawab salah satu assessment Anda sebelumnya tentang `Codable`.

---

## Apa sebenarnya Codable?

Misalnya server mengirim:
```
{
  "id": 17,
  "name": "Dede"
}
```

Swift menerima data mentah.
Secara konsep:
```
Internet
↓
JSON bytes
↓
JSONDecoder
↓
User
```

Kode:
```
let user = try JSONDecoder().decode(
    User.self,
    from: data
)
```

Artinya:
> Ambil `data`, baca JSON-nya, lalu coba bentuk menjadi `User`.

Misalnya:
```
struct User: Codable {
    let id: Int
    let name: String
}
```

JSON:
```
{
  "id": 17,
  "name": "Dede"
}
```

cocok.

Hasilnya:
```
user.id
// 17

user.name
// "Dede"
```

---

## Tetapi tipe harus cocok

Kalau Swift meminta:
```
let id: Int
```

tetapi server mengirim:
```
{
  "id": "17"
}
```

perhatikan bahwa:
```
17
```

dan:
```
"17"
```

berbeda.

Yang pertama:
```
number
```

Yang kedua:
```
String
```

Jadi model:
```
let id: Int
```

bisa gagal decode jika backend ternyata mengirim `"17"` sebagai String.

Ini kasus yang sangat umum saat mengintegrasikan aplikasi dengan backend lama.

---

## Field hilang juga penting

Misalnya:
```
struct User: Codable {
    let id: Int
    let name: String
    let phone: String
}
```

Tetapi JSON:
```
{
  "id": 17,
  "name": "Dede"
}
```

`phone` sama sekali tidak ada.

Swift berharap:
```
phone wajib
```

tetapi JSON tidak menyediakannya.
Decode gagal.

Kalau backend memang boleh tidak memberikan `phone`, model sebaiknya:
```
let phone: String?
```

Maka ini aman.

---

## `null` versus field tidak ada

Untuk Optional sederhana seperti:
```
let phone: String?
```

`Codable` biasanya dapat menangani dua kondisi berikut.

JSON dengan `null`:
```
{
  "phone": null
}
```

atau JSON tanpa `phone`:
```
{
}
```

hasil Swift:
```
phone == nil
```

Ini salah satu alasan Optional sangat penting dalam model API.

## Contoh realistis

Server:
```
{
  "id": 102,
  "name": "Ahmad",
  "email": "ahmad@example.com",
  "phone": null,
  "age": 31
}
```

Model:
```
struct Teacher: Codable {
    let id: Int
    let name: String
    let email: String
    let phone: String?
    let age: Int
}
```

Lalu:
```
let teacher = try JSONDecoder().decode(
    Teacher.self,
    from: data
)
```

hasil:
```
teacher.id
→ 102

teacher.name
→ Ahmad

teacher.phone
→ nil
```

Kemudian UI bisa:
```
Text(teacher.phone ?? "Belum ada nomor telepon")
```

Sekarang mulai terlihat hubungannya:
```
JSON
↓
Codable
↓
Optional
↓
Swift model
↓
SwiftUI
```

Ini pola yang sangat sering Anda gunakan sebagai iOS developer.

## Bug nyata yang harus bisa Anda bedakan

Kasus A:
```
No internet connection
```

Artinya request mungkin tidak pernah berhasil mendapatkan response.

Kasus B:
```
HTTP 500
```

Artinya server menjawab, tetapi server mengalami masalah.

Kasus C:
```
DecodingError
```

Artinya data kemungkinan sudah diterima, tetapi format JSON tidak cocok dengan model Swift.

Kasus D:
```
Unexpectedly found nil while unwrapping...
```

Artinya Swift runtime menemukan Optional nil yang dipaksa menggunakan `!`.

Empat kasus itu berbeda.

Developer jangan menyebut semuanya:
> “Gangguan jaringan.”

Ini kebiasaan yang nanti kita hilangkan.

## Bagaimana developer menyelidiki decoding error?

Misalkan kode:
```
do {
    let user = try JSONDecoder().decode(
        User.self,
        from: data
    )
} catch {
    print(error)
}
```

Kemudian muncul error.

Jangan langsung mengubah model secara acak.

Periksa:
```
1. JSON aktual dari server
2. nama field
3. tipe field
4. apakah field bisa null
5. apakah field kadang hilang
6. model Swift
```

Contoh:
Swift:
```
let teacherId: Int
```

Server:
```
"teacherId": "1692"
```

Diagnosis:
```
Swift meminta Int
Server memberi String
```

Bukan:
```
URLSession rusak
```

## CodingKeys

Backend kadang mengirim nama:
```
{
  "teacher_id": 1692,
  "teacher_name": "Dede"
}
```

Tetapi Swift biasanya kita ingin:
```
teacherId
teacherName
```

Kita tidak harus mengikuti snake_case dalam seluruh aplikasi.

Bisa:
```
struct Teacher: Codable {
    let teacherId: Int
    let teacherName: String

    enum CodingKeys: String, CodingKey {
        case teacherId = "teacher_id"
        case teacherName = "teacher_name"
    }
}
```

Artinya:
```
JSON teacher_id
↓
Swift teacherId
```

dan:
```
JSON teacher_name
↓
Swift teacherName
```

Nanti Anda akan sering melihat `CodingKeys`.
