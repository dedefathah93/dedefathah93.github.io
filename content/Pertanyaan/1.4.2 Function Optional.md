Perhatikan:

```
func validateScore(
    score: Int
) -> String? {

    guard score >= 0 else {
        return "Nilai tidak boleh negatif"
    }

    guard score <= 100 else {
        return "Nilai maksimal 100"
    }

    return nil
}
```

Jawab:

1. Kenapa return type function adalah `String?`, bukan `String`?
2. Apa hasil `validateScore(score: -10)`?
3. Apa hasil `validateScore(score: 120)`?
4. Apa hasil `validateScore(score: 80)`?
5. Kalau hasilnya `nil`, secara konsep artinya apa?
6. Apakah function akan mengecek `score <= 100` jika `score = -10`? Jelaskan.
7. Apa fungsi `return nil` paling bawah?
8. Menurut Anda kenapa validasi seperti ini lebih baik dipisahkan ke function dibanding menaruh semua kondisi langsung di SwiftUI `Button`?

Jawaban:
1. karena -> mengembalikan nilai. kalau yang dikembalikan dibatasi dengan String mau tidak mau syntax harus ada error atau tidak menerima valid, sedangkan di akhir ada return nil
2. Nilai tidak boleh negatif
3. Nilai maksimal 100
4. nil
5. secara konsep dia valid
6. tidak, karena ada return maka dia berhenti pada return Nilai tidak boleh negatif
7. mengembalikan nilai
8. saya kurang faham, tapi akan saya coba jawab, karena Button bagusnya bisa dipencet ketika semua kondisi sudah terpenuhi. dan kenapa kita simpan dalam sebuah function untuk mengetahui lebih awal dimana letak kekurangannya

Tanggapan:
Jawaban 1 sampai 7 sudah benar secara konsep. Nomor 8 juga sudah mengarah ke alasan yang tepat, hanya perlu kita rapikan secara engineering.

Untuk nomor 1, inti jawaban Anda benar. Karena function bisa menghasilkan pesan error atau tidak ada error, return type-nya harus:

```
String?
```

Bukan:

```
String
```

Karena `String` mewajibkan selalu ada nilai String, sedangkan kita memang membutuhkan kondisi:

```
ada error  → String
valid      → nil
```

Untuk nomor 7, `return nil` bukan sekadar “mengembalikan nilai”. Lebih spesifik:

```
semua guard lolos
↓
tidak ditemukan masalah
↓
return nil
↓
validasi berhasil
```

Sekarang bagian nomor 8 adalah konsep penting.

Misalnya kita menulis semua validasi langsung di Button:

```
Button("Simpan") {
    if score < 0 {
        // tampilkan error
    } else if score > 100 {
        // tampilkan error
    } else {
        // simpan
    }
}
```

Secara teknis bisa.

Tetapi kalau aplikasi makin besar, Button akan mulai mengerjakan terlalu banyak pekerjaan:

```
Button
├── validasi
├── hitung data
├── cek login
├── buat request
├── simpan database
├── menangani error
└── mengubah UI
```

Akhirnya kode sulit dibaca dan sulit diuji.

Lebih baik:

```
func validateScore(score: Int) -> String? {
    ...
}
```

kemudian Button hanya:

```
Button("Simpan") {
    let error = validateScore(score: score)

    if let error = error {
        errorMessage = error
        return
    }

    save()
}
```

Sekarang pembagian tanggung jawabnya lebih jelas:

```
validateScore()
→ tugasnya validasi

Button
→ tugasnya merespons tindakan user
```

Ini konsep besar dalam software engineering:

```
satu bagian kode
sebaiknya punya
satu tanggung jawab utama
```

Nanti kita akan bertemu istilah:

```
Separation of Concerns
```

dan prinsip seperti:

```
Single Responsibility
```

Belum perlu dihafal sekarang, tapi pola pikirnya mulai dibangun dari sini.

Nomor 8 Anda tadi juga menyebut:

> Button bagusnya bisa dipencet ketika semua kondisi sudah terpenuhi.

Itu bisa menjadi strategi UI lain.

Misalnya:

```
Button("Simpan") {
    save()
}
.disabled(score < 0 || score > 100)
```

Tapi ini tidak menggantikan validasi logic.

Kenapa?

Karena UI bisa saja salah, berubah, atau function dipanggil dari tempat lain.

Jadi biasanya kita punya dua lapisan:

```
UI prevention
+
business validation
```

Contoh:

```
Button dinonaktifkan
→ UX lebih baik

validateScore()
→ tetap menjaga data valid
```

Jangan hanya mengandalkan UI.
